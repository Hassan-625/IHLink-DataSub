# Android app access and mobile wallet changes

The Android preview installs an app-local `NativeVault` Capacitor plugin. Auth persistence uses app-private preferences with AES-GCM ciphertext, wrapped by an Android Keystore AES key. Enabling an app passcode adds a PBKDF2-HMAC-SHA256-derived AES-GCM layer (310,000 iterations, random 32-byte salt). Six-digit passcodes stay separate from four-digit server-verified purchase PINs. PINs and auth tokens are not written to JavaScript localStorage. Existing localStorage auth tokens are removed; existing preview users sign in once before enabling the new passcode.

The vault locks on backgrounding. Five incorrect passcode attempts wipe only local app access and require a full sign-in. Optional fingerprint uses AndroidX BiometricPrompt with BIOMETRIC_STRONG and a CryptoObject wrapping a biometric-protected Keystore key; enrolling a new biometric invalidates that key. Changing the app passcode disables the previous biometric wrapper. Android backup/device-transfer rules exclude app data. iOS currently keeps its existing sign-in flow; equivalent iOS local passcode access is not implemented by this Android change.

Transfers locate an active DataSub BillStack virtual account but move existing balances internally. They do not initiate external BillStack payouts or fabricate webhook deposits. The database verifies purchase PINs, locks both wallets in UUID order, conserves balances and writes paired ledger entries atomically. Requests use sender-scoped idempotency keys. An uncertain client response preserves its request and freezes transfer details until the same request is confirmed, including after an app restart. No real transfers were performed during development verification.

Referral rewards start disabled. The Control Center configures terms and manually verifies each reward using an actual successful transaction after the invitation, with enough recorded profit to cover the reward. One reward per invited account is enforced. Approved referral earnings are separate until moved into the wallet once under a row lock. Later refunds and suspected abuse require finance review; already-approved promotional rewards are not automatically clawed back.

Typecheck, production builds and isolated database tests verify the implemented code. Native compilation and emulator smoke checks are release checks; passcode and fingerprint acceptance on a physical device, real transfers and full live provider purchase/refund tests remain separate acceptance work. Release signing and Google/Apple submissions require the owner’s production credentials.
